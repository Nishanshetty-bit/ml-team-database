# ML-01 database handoff contract

This document describes the database-side handoff for the ML-01 developer. It does
not contain or implement the ML-01 model.

## Shared source data

The unified database's shared input entities are in the `core` schema. The current
database definition includes these relevant tables:

- `core.core_users`
- `core.core_profiles`
- `core.core_match_preferences`
- `core.core_discovery_gender_preferences`
- `core.core_interests`
- `core.core_user_interests`
- `core.core_intents`
- `core.core_user_intents`
- `core.core_blocks`
- `core.core_relations`
- `core.core_connections`
- `core.core_connection_requests`
- `core.core_discovery_dismissals`
- `core.core_user_consents`

The model should read only the fields it needs and must respect active/visible users,
blocks, dismissals, consent, and other eligibility rules defined by the ML-01 team.

## ML-01 output table

`core.ml01_candidate_output` is the candidate-pair result table. The database definition
currently contains:

| Column | Meaning |
|---|---|
| `candidate_pair_id` | Unique identifier for the generated viewer/candidate pair |
| `viewer_user_id` | User for whom candidates are generated |
| `candidate_user_id` | Candidate user |
| `viewer_age` | Viewer age snapshot, if used |
| `candidate_age` | Candidate age snapshot, if used |
| `viewer_gender` | Viewer gender snapshot, if used |
| `candidate_gender` | Candidate gender snapshot, if used |
| `shared_interests` | JSON array of shared interests |
| `compatible_intents` | JSON array of compatible intents |
| `candidate_source` | Source/rule reason for candidate inclusion |
| `generated_at` | Generation timestamp |

## ML-01 to ML-02 handoff

`ml02.ml01_eligibility_input` is the downstream handoff table. It currently contains:

| Column | Meaning |
|---|---|
| `eligibility_input_id` | Database-generated row identifier |
| `viewer_user_id` | Viewer |
| `eligible_candidate_user_ids` | Array of eligible candidate user IDs |
| `eligibility_status` | Status of the eligibility result |
| `candidate_generation_reason_codes` | Array of reason codes |
| `eligibility_rule_version` | Version of ML-01 eligibility logic |
| `processing_status` | Handoff processing status |
| `received_at` | Handoff timestamp |

The ML-01 developer should write the final per-viewer candidate list to this table only
after the team confirms the agreed output semantics. The pair-level rows in
`core.ml01_candidate_output` and the per-viewer array in `ml02.ml01_eligibility_input`
serve different purposes; they are not interchangeable.

## Important integration note

Before coding the database adapter, the ML-01 owner and ML-02 owner must confirm:
1. Whether ML-01 writes both output tables or only the ML-02 handoff.
2. Exact meaning and allowed values for `eligibility_status` and `processing_status`.
3. Whether `candidate_pair_id` is generated by the model or by the database.
4. Whether the candidate list must be ordered, and whether duplicates are prohibited.

Do not assume a Python column type from this document alone. Use the exported live schema
and `information_schema.columns` as the source of truth.
